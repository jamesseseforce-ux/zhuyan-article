# 开发验收用例

版本：1.0.0 / release-1。以下是输入与语义验收条件，不是已执行的模型测试成绩；不按指定措辞或句长评分。运行时保存输入、实际输出及版本，再由人核对。

## 使用引导与作者提示回归

| ID | 请求或上下文 | 应核对的结果 |
|---|---|---|
| U01 | 用户只问“怎么用”，尚未提供文章 | 给1–2个相关提问示例，请用户附原文；不推销、不展示电话 |
| U02 | 用户已提供文章与明确改写范围 | 直接编辑，不重复教程、不强迫填写表单 |
| U03 | 用户首次问“作者是谁” | 回答崔凯律师，并在对话中提供一次配置的咨询提示；不虚构履历 |
| U04 | 同一对话已给过电话，随后再遇复杂法律问题或作者询问 | 不再次主动展示咨询提示或电话号码；仍正常处理能力范围内的任务 |
| U05 | 普通法律科普润色或非法律文章 | 不仅因“法律”关键词出现就提示律师咨询 |
| U06 | 复杂法律文书处理且本对话未提示过，交付有纯正文文件 | 咨询提示只在对话说明中出现一次，不进入正文文件，不阻断任务或自动联系律师 |
| U07 | 用户询问版权及第三方规则的使用许可 | 告知项目声明的适用范围，保留第三方原许可，不宣称所有上游规则均为崔凯律师原创 |

上述是验收场景，本次只作规则一致性审阅，尚未进行独立多轮模型行为测试。

## 当前最需要的外部测试

用未参与调优的新文章与历史失败稿分开记录。每次冻结实际提交全文、版本及文件哈希，完整保留输出，不删除标黄段落后仍称原版本。已上传的用户文章仅用于本地编辑，未经授权不自动提交第三方检测。

文章质量先核对：原意、条件、责任、引用、作者立场、长稿信息量及阅读条理。有任何重要损失，不因分数变高而通过。

朱雀目标：人工≥80%、疑似≤20%、AI＝0。提交新版本后才能填写实际三项比例；所有规则整合和本地验证都不能代填。截图只能提供可见文字比对，不能代替平台导出的全文逐字比对。没有足够新稿成绩，不宣布跨题材稳定达标。

记录一篇原稿的各版本时，它们属于同一原稿，不扩大独立样本数；同图重复上传、页面重复饼图不增加复测次数。具体次数、时间、入口不知道就记未知，不以“不像AI”的主观感觉替代结果。

R10/R11 回归提醒：两份由同一助手拟出的不同主题初稿均未检测，只测最终稿；因此只可判断各稿是否达到目标，不能计算改写前后变化，更不能从两篇不同主题的分数差推断句式或题材的因果作用。后续要评价改写收益，应在同一篇原稿上分别冻结并检测原稿与改写稿，保留每份实际提交的全文和版本。新增写作规则还须指出可复核的文本问题、说明其对读者理解或保真的影响；仅有检测色块或分数不足以确立规则。
